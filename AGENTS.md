# Project Notes For Codex

## Local Search Rules

- На этой машине `rg`/`ripgrep` в проекте может падать с `Access is denied`.
- Текстовые файлы проекта обычно сохранены как UTF-8 без BOM, а Windows PowerShell 5.1 без явного параметра читает их как ANSI/1251 и ломает русскоязычный текст в mojibake.
- Для чтения текстовых файлов всегда указывать `-Encoding UTF8`: `Get-Content -LiteralPath path\to\file.py -Encoding UTF8`.
- Для поиска по содержимому всегда указывать `-Encoding UTF8` у `Select-String`: `Get-ChildItem -Recurse -File | ... | Select-String -Pattern '...' -Encoding UTF8`.
- Если вывод снова выглядит как `РќР°...` или `Р”Рѕ...`, считать чтение некорректным и повторить команду с явным `-Encoding UTF8`, не делать выводы по битому тексту.
- Для поиска по файлам сразу использовать обычный PowerShell-поиск: `Get-ChildItem -Recurse -File | Select-String -Pattern '...' -Encoding UTF8`.
- Для поиска конкретных файлов использовать `Get-ChildItem -Recurse -Filter ...` или `Get-ChildItem -Recurse -File | Where-Object { ... }`.
- Никогда не читать и не искать без явной необходимости в тяжелых/сгенерированных каталогах: `__pycache__`, `.git`, `.venv`, `venv`, `.idea`, `dist`, `build`, `.cache`, `coverage`, `tmp`, `temp`.
- При рекурсивном PowerShell-поиске всегда исключать такие каталоги до `Select-String`, чтобы не забивать контекст и не тратить токены на зависимости, кеши, IDE-файлы, сборочные артефакты и бинарные файлы.
- Если для задачи все-таки нужен файл внутри такого каталога, читать только конкретный известный файл или короткий точечный фрагмент, а не запускать широкий поиск по всему каталогу.

## Project Shape

- Это небольшой Python/FastAPI-сервис для удаленного управления WireGuard/AmneziaWG-пирами.
- Основная точка входа: `wg-manager.py`.
- Локальные настройки и секреты лежат в `private_conf.py`; не логировать и не раскрывать реальные значения секретов.
- Runtime-состояние WireGuard ожидается вне репозитория: `/etc/wireguard/wg0.conf`, `/etc/wireguard/clients.json`, интерфейс `wg0`.
- Runtime-состояние AmneziaWG ожидается внутри Docker-контейнера Amnezia, по умолчанию `amnezia-awg2`: конфиг `/opt/amnezia/awg/awg0.conf`, таблица клиентов `/opt/amnezia/awg/clientsTable`, userspace-процесс `amneziawg-go awg0`.
- Сервис создает клиентские ключи, PSK, IPv4/IPv6 адреса, добавляет `[Peer]` в конфиг, применяет изменения через `wg syncconf` для WireGuard или через `docker exec <AWG_CONTAINER_NAME> bash -lc 'awg syncconf awg0 <(awg-quick strip /opt/amnezia/awg/awg0.conf)'` для AmneziaWG, удаляет peer и отдает статус.
- Endpoint `VK_TURN_ENDPOINT` относится к связке с `vk-turn-proxy`; изменения вокруг него делать осторожно и явно проверять ожидаемый формат клиентского конфига.
- Узел имеет handshake route `/handshake`, который панель дергает при добавлении узла и получает JSON с полем `version`.
- Если у удаленного узла нет `/handshake`, панель должна считать такой узел legacy-узлом версии `1`.
- Текущая версия узла задается константой `NODE_VERSION` в `wg-manager.py`; старые WireGuard-узлы считаются версией `1`, узлы с режимом AmneziaWG считаются версией `2`.

## Safety Rules

- Не выполнять команды, которые меняют реальный WireGuard/AmneziaWG-сервер (`wg set`, `wg syncconf`, `awg syncconf`, `docker restart`, запись в `/etc/wireguard/...` или в `/opt/amnezia/awg/...` внутри контейнера), без явного понимания задачи и подтверждения, что это нужно именно сейчас.
- При разработке и тестах предпочитать временные файлы, моки `subprocess` и переопределяемые пути вместо работы с настоящим `/etc/wireguard`.
- Не коммитить реальные приватные ключи, PSK, API-ключи, IP-адреса боевых серверов и содержимое клиентских конфигов.
- При добавлении диагностических сообщений маскировать секреты: показывать только короткий префикс/суффикс или длину значения, если это действительно нужно для отладки.
- Не менять существующие незакоммиченные правки пользователя без необходимости; если файл уже изменен, сначала понять текущий diff.

## Logging Rules

- Все новые и изменяемые логи писать на русском языке.
- Каждый лог должен начинаться с контекста функции или этапа в формате `"[function_name]"`.
- Пример: `print(f"[sync_wg] Применяем конфигурацию WireGuard для интерфейса {WG_INTERFACE}")`.
- Логи должны помогать разбирать поведение кода и отладку, а не существовать для галочки.
- Избегать бессмысленного спама в логах, но не избегать полезных логов.
- В логах нельзя печатать полный `X-API-Key`, приватные ключи клиентов, PSK и другие секреты.

## Code Rules

- Сохранять простой стиль проекта: обычные функции, FastAPI-модели Pydantic и минимальные зависимости.
- Форматировать строки через `f"чтото {variable}"`, если только не оправдано иное.
- Для работы с JSON использовать `json.load`/`json.dump`, а не ручную сборку строк.
- Для работы с системными командами предпочитать `subprocess` со списком аргументов. `shell=True` использовать только когда без shell-пайплайна реально проще и безопасно.
- Ошибки API отдавать через `HTTPException` с понятным русским `detail`, если это пользовательская или эксплуатационная ошибка.
- При изменении логики выдачи адресов следить, чтобы `clients.json`, `AllowedIPs` в `wg0.conf`/`awg0.conf` и возвращаемый клиентский JSON оставались согласованными.
- При изменении API-ответов учитывать совместимость клиентов, которые уже могут ожидать поля `private_key`, `address`, `server_public_key`, `endpoint`, `allowed_ips`, `mtu`, `persistent_keepalive`, `preshared_key`, `config_name`.
- `/create` без поля `mode` должен оставаться WireGuard-совместимым. Для AmneziaWG панель отправляет `mode: "amnezia"` или алиас `awg`/`amneziawg`.

## Roadmap Rules

- Если появится `roadmap.md`, периодически поглядывать в него перед реализацией новых фич, инфраструктурных задач и уборки технического долга.
- Если в текущей задаче была прямо сейчас реализована фича или техзадача, уже упомянутая в `roadmap.md`, обновить соответствующий пункт в `roadmap.md` отметкой `реализовано YYYY-MM-DD`.
- Не начинать выполнять задачи из `roadmap.md` только из-за их наличия в файле: это список отложенных задач, а не автоматический план на текущую сессию.

## Testing Rules

- Для проверки синтаксиса Python можно использовать `python -m py_compile wg-manager.py`.
- Для будущих автотестов предпочитать `pytest` с моками `subprocess.check_output`, `subprocess.check_call`, файловых путей WireGuard/AmneziaWG и FastAPI `TestClient`.
- Обычные тесты не должны требовать установленного `wg`/`awg`, root-прав, активных интерфейсов `wg0`/`awg0`, настоящего `/etc/wireguard` или Docker-контейнера `amnezia-awg2`.
- Live-проверки AmneziaWG выполняются только на VPS с настоящим контейнером через `curl` к node API и `docker exec amnezia-awg2 ...`; правильный интерфейс официального AWG2-контейнера — `awg0`, а не `wg0`.
- Перед запуском команд, которые могут сходить в сеть или установить зависимости, учитывать sandbox/approval правила текущей среды.

## Module Documentation

- В проекте может появиться папка `docs/` со списком doc-файлов по отдельным сложным местам проекта.
- Если работа затрагивает такое место и соответствующий файл существует, сначала обратиться к нему.
- Если изменение кода меняет актуальность такого doc-файла, обновить этот doc-файл в той же задаче.
- Doc-файлы по сложным местам проекта хранить в папке `docs/`.
- Каждый такой doc-файл должен быть умеренно наглядным для человека и удобным для ИИ: писать кратко, однозначно, структурно и без лишней воды.
- Там, где это помогает понять или проверить описание, doc-файл должен ссылаться на реальные файлы проекта, функции и строки кода.

## Legend Documentation

- В проекте может быть отдельный набор legend-doc файлов: это документы про внешние знания, протоколы, API, сервисы и сетевую механику, связанную с проектом.
- Legend-doc отличается от module-doc тем, что описывает не внутреннее устройство нашего кода, а внешний мир, с которым проект взаимодействует.
- Legend-doc файлы хранить в папке `docs/legend/`.
- Если задача затрагивает внешний сервис, протокол или API, для которого уже есть legend-doc файл, сначала обратиться к нему.
- Если в ходе работы обнаружена новая важная информация о WireGuard, AmneziaWG, FastAPI, `wg`, `awg`, `wg-quick`, `awg-quick`, `syncconf`, `vk-turn-proxy`, сетевых ограничениях, форматах конфигов или надежном способе проверки, обновить соответствующий legend-doc файл в той же задаче.
- Если подходящего legend-doc файла нет, но знание явно повторно пригодится проекту, создать новый файл в `docs/legend/`.
- Legend-doc должен быть практичным: фиксировать проверенные наблюдения, рабочие способы взаимодействия, известные ограничения, риски, примеры запросов/ответов и ссылки на источники, если они есть.
- Непроверенные гипотезы можно записывать только в отдельном разделе `Гипотезы`, явно помечая их как непроверенные.
- Устаревшие сведения не удалять молча: переносить в раздел `Устарело` или заменять с кратким пояснением, почему информация больше неактуальна.
